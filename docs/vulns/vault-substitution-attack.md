# Vault Substitution Attack (fixed)

**envvault** is a CLI tool for encrypting `.env` files in a safe manner.
It also provides a way to share `.env` files with other parties via asymmetric algorithms.
However, it uses the same interface for unlocking an encrypted file and reading a shared file.
As a result, an attacker could overwrite an encrypted `.env` file with arbitrary content encrypted using the victim's public key. Because the victim uses the same interface for reading locked files and shared files, envvault silently accepts the overwritten file as a regular encrypted file. This could be abused in CI/CD pipelines and other critical environments.

## Scenario

Let's say the victim has an Age X25519 keypair:

```bash
$ envvault keygen
🔑 Keypair generated!
Public key:  age1e4j88gcaxfudjk6xtgskvyrl3j5e9rkzevx9h4m4xyn2d8gn9d4swlx0fv
Private key: saved to /home/faramin/.envvault/keys.txt (keep this secret!)

$ cat ~/.envvault/keys.txt
# generated by envvault
AGE-SECRET-KEY-1ANF96TVGTSLA93S4T9JW9W5TW3SDWPR8YAA5DFV0GHSRFYA97ZJS5PGGYY
```

We have a directory with an `.env` file.

```bash
$ ls -a
.  ..  .env
$ cat .env
secret=very_secret
$ envvault lock .env --allow-weak
Enter password:
Confirm password:
⚠️  Warning: Password is weak (score 0/4, crack time: instant). Proceeding anyway.
🔒 Encrypted .env → .env.vault (aes256gcm-argon2id)
$ envvault export .env.vault
Enter password:
secret=very_secret

🔓 Exported .env.vault
```

Everything works as expected.

Now an attacker could create another `.env` file and overwrite the user's original file:

```bash
$ # - ATTACKER SIDE -
$ # First, we make sure the attacker does not have the private keys:
$ mv ~/.envvault ~/.envvault.bck
$ ls ~/.envvalut
ls: cannot access '/home/faramin/.envvalut': No such file or directory
$ # Now, let's encrypt the new '.env' file using the sharing method:
$ ls -a
.  ..  .env  .env.vault  .overwrite.env
$ cat .overwrite.env
secret=OVERWRITE
$ envvault lock -a age-pubkey -r age1e4j88gcaxfudjk6xtgskvyrl3j5e9rkzevx9h4m4xyn2d8gn9d4swlx0fv .overwrite.env
🔒 Encrypted .overwrite.env → .overwrite.env.vault (age-pubkey)
$ cp .env.vault .env.vault.bck
$ cp .overwrite.env.vault .env.vault
$ # - VICTIM SIDE -
$ # The victim has their own private keys, so move the config directory back:
$ rm -rf ~/.envvault
$ cp -r ~/.envvault.bck ~/.envvault
$ envvault export .env.vault
secret=OVERWRITE

🔓 Exported .env.vault
```

So, an attacker can overwrite the `.env` file using only the victim's public key, and envvault accepts it silently.

Now let's say a program reads this secret environment variable and uses it for authentication:

```go
package main

import (
	"fmt"
	"os"
	"strings"
)

func main() {
	secret := strings.TrimSpace(os.Getenv("secret"))
	if secret == "" {
		fmt.Println("empty secret")
		os.Exit(1)
	}

	fmt.Printf("Enter secret: ")
	var input string
	if _, err := fmt.Scanln(&input); err != nil {
		fmt.Println(err.Error())
		os.Exit(1)
	}
	input = strings.TrimSpace(input)

	if input == secret {
		fmt.Println("Pass!")
	} else {
		fmt.Println("Fail!")
	}
}
```

```bash
$ envvault run .env.vault -- go run auth.go
Enter password for .env.vault:
Enter secret: OVERWRITE
Pass!
```

## Fixing Suggestion

The core issue is that envvault uses the same interface for both reading an encrypted file and reading a shared file. An attacker could abuse this by injecting a shared file that is accepted as a legitimate encrypted `.env` file.

Simply separating `unlock`/`run`/`export` from the sharing mechanism only closes the age-pubkey case; an attacker with write access to the vault path could just as easily substitute a password-locked vault (encrypted under a password they choose) and it would be accepted the same way, since nothing binds a vault file to the specific `lock` operation that was supposed to have produced it.

## Fix (implemented)

`envvault` now maintains a local trust store (`~/.envvault/trust.json`, outside any repo/CI-checkout-controlled path) that pins the algorithm — and, for public-key algorithms, the recipient set — a vault was locked with:

- `envvault lock` records this pin automatically (opt out with `--no-trust`).
- `envvault unlock`, `export`, `run`, and `share` check a vault's actual header against its pin *before* any credential prompt or decryption attempt. A mismatch (wrong algorithm or wrong recipients) is rejected immediately with an explanatory error, regardless of whether the substituted content happens to be decryptable with the victim's own key.
- A vault with no pin yet (e.g. a fresh CI checkout) is still allowed through, with a warning, to avoid breaking first-time use — `envvault trust <file>` lets an operator pin it explicitly once they've verified its contents out-of-band, and `envvault trust <file> --algorithm ... --recipient ...` lets CI pre-register expected values from a secret before the vault file is even fetched, so the very first access is already protected.

See `crypto/trust.go`, `cmd/trust.go`, and the `enforceTrust` calls in `cmd/unlock.go`, `cmd/export.go`, `cmd/run.go`, `cmd/share.go`.

Not addressed by this fix: a full cryptographic signature over the envelope (e.g. Ed25519) would be a stronger, defense-in-depth follow-up, since the current pin is only as good as the local trust store's integrity and isn't portable across machines the way a signature would be.
